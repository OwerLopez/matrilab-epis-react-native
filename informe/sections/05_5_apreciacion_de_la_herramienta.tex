\phantomsection\addcontentsline{toc}{section}{5. Apreciación de la herramienta}

La valoración se basa en lo que el equipo observó al construir y probar MatriLab con React Native y Expo.

\vspace{0.2cm}
\phantomsection\addcontentsline{toc}{subsection}{5.1 Características favorables}
\colabtitle{5.1 Características favorables}

\subsubtitulo{A. Interfaces nativas reales a partir de un solo código}

Cada componente del núcleo se convierte en una vista nativa del sistema [2]. En las capturas se ve que el interruptor de la configuración es el de Android, el teclado y la hoja de compartir son los del teléfono, los diálogos de anular y guardar son los del sistema y la pila de navegación usa las transiciones y el gesto de retroceso nativos. Con ese mismo código, sin cambios, la aplicación se exportó a la web (Figura \ref{fig:web}). Las diferencias por plataforma que sí hubo que escribir fueron mínimas: el comportamiento del teclado y el efecto ripple de Android. Para un proyecto que debe llegar a estudiantes con Android y con iPhone, esto reduce a la mitad el trabajo frente al desarrollo nativo separado.

\subsubtitulo{B. Ciclo de desarrollo rápido y ecosistema JavaScript}

Con Expo Go no fue necesario compilar proyectos de Android Studio: el emulador cargaba la aplicación desde Metro (Figura \ref{fig:metro}) y \textit{Fast Refresh} aplicaba cada cambio de estilo en uno o dos segundos conservando el estado de la pantalla, lo que permitió ajustar márgenes, columnas y colores viendo el resultado al instante. El ecosistema aportó piezas maduras: TypeScript detectó errores de navegación entre pantallas antes de ejecutarlas, una librería resolvió el código QR y Jest probó las reglas de negocio en segundos. El mismo lenguaje sirvió para la aplicación, las pruebas y el recorrido automatizado de capturas.

\vspace{0.2cm}
\phantomsection\addcontentsline{toc}{subsection}{5.2 Características desfavorables}
\colabtitle{5.2 Características desfavorables}

\subsubtitulo{A. Dependencia de la compatibilidad entre versiones}

Una aplicación React Native depende de una cadena de versiones que deben coincidir: Expo SDK, React Native, React, cada librería con código nativo y la versión de Expo Go instalada en el teléfono, que solo abre proyectos de su mismo SDK. Fue obligatorio instalar las dependencias con el instalador de Expo para no romper esa cadena. El ritmo de cambios también se notó: el SafeAreaView del núcleo figura como obsoleto [16], la Nueva Arquitectura cambió el comportamiento interno de varias librerías y TypeScript 6 dejó de incluir tipos globales por defecto, lo que obligó a corregir la configuración (cambio 6). En un proyecto que dure varios semestres, actualizar dependencias requiere tiempo dedicado.

\subsubtitulo{B. Layout limitado a Flexbox y diferencias entre plataformas}

React Native solo ofrece Flexbox y posición absoluta: no hay CSS Grid ni \textit{media queries}. La cuadrícula del horario tuvo que calcularse a mano con las dimensiones de la ventana y posición absoluta, y la rejilla adaptable de laboratorios obligó a volver a crear la lista al cambiar de ancho. Algunos componentes se comportan distinto en cada sistema (teclado, sombras, ripple) y hay que probar en ambos. Además, lo que ocurre del lado nativo exige conocer las herramientas de Android: los permisos de cámara de Expo Go, el teclado del emulador y la rotación tuvieron que resolverse desde la línea de comandos del emulador.
